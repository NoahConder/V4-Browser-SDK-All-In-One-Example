# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

iPhone-style web dialer using SignalWire's Fabric/WebRTC stack. It's a hands-on testing tool for the SignalWire Browser SDK, not a production app — weigh hardening against convenience accordingly. Two services:

- `backend/` — Flask app on port **5001**. Mints SignalWire subscriber tokens and lists the space's resources. It does **not** route media or signaling.
- `frontend/` — Vite + React + TypeScript on port **5173**. All WebRTC (signaling, media, DTMF) goes through the published npm package `@signalwire/js` (`^4.0.0-rc.5` in `frontend/package.json`, `4.0.0-rc.5` in the lockfile; it is npm's `latest`/`rc` tag — there is no stable `4.0.0`). `vite.config.ts` resolves it from `node_modules` like any other dependency; there is no local SDK checkout. To read SDK internals, clone `signalwire-js` yourself at the matching tag (its `examples/` are the authoritative v4 API guide, `packages/main/src/` the source) or read `node_modules/@signalwire/js/dist/index.mjs`. Never edit the SDK from here; consume the npm package.

`README.md` is written for SignalWire customers (setup, usage, an SDK-feature-to-file map). `CHANGELOG.md` holds the fork's history relative to upstream `briankwest/swdialer`. This file holds what you need to work on the code.

## Rules

One line each; the section named in parentheses holds the reasoning. Read it before relaxing a rule.

- The frontend never stores or caches tokens; the SDK calls the `credentialProvider` callbacks on demand. (Token lifecycle)
- Never call `signalWireService.disconnect()` from a hook cleanup. Only `App.tsx`'s `beforeunload` does, and not while `hasActiveCall()`. (Singleton lifetime; Reattach)
- Don't change `beforeunload`, the `calls$` adoption, or the `persistSession` omission in isolation. (Reattach)
- `endCall()` calls `handleCallEnded()` before `await call.hangup()`. Don't reorder. (Call-ended detection)
- Don't simplify `refusalOf()` back to a bare `await call.transfer()`/`toggleHold()`. (Transfer and hold)
- Transfer is hidden behind `SHOW_TRANSFER` (`false`) in `CallScreen.tsx`; keep `TransferModal.tsx`, `transferCall` and the skipped spec so flipping it restores the feature, and keep README/CHANGELOG silent on transfer. (Transfer and hold)
- High-frequency observables never go through `useCallStore`. (High-frequency observables)
- Don't drop the `no_inbound_video` filter in `relevantIssues()` without re-testing an audio-only call. (Call quality vs. health)
- Don't remove the remote-audio fallback without verifying audio on an inbound and an outbound call. (Remote audio)
- The speaker bar reads `services/remoteAudioMeter.ts`, fed from `handleRemoteMedia()`, never `call.remoteAudioLevel$` (rc.5 emits 0). (Remote audio)
- Don't enable `savePreferences` or `persistSession` on the SDK client. (Settings; Reattach)
- Mute is local. Don't switch it to the SDK's `self.mute()`. (Mute)
- `toggleScreenShare` runs directly from the click with no `await` before `startScreenShare()`; `endCall()` stops a share before hanging up. (Screen share)
- Window-level key handlers filter their targets and read the latest handler through a ref. (Key handlers)
- Every `/api` route goes through `gate()`. Token minting must never be open. (Backend gate)
- No bare `console.*`; use `utils/log.ts`. (Conventions)
- Keep number normalization and dial-address detection in sync between `signalwire.ts`/`address.ts` and `utils/signalwire.py`, and update the shared fixture. (Conventions)
- The field is the dial string: `useDialFieldStore` keeps `wantsVideo` and a Fabric address's `?channel=` in step (`withChannel`/`channelOf` in `address.ts`); `makeCall` only normalizes, passes `receiveVideo` explicitly and adds `from` for a phone number. (Per-channel dialing)
- Joining with the camera off is hidden behind `SHOW_CAMERA_OFF_JOIN` (`false`) in `useDialFieldStore.ts`; keep `cameraOff`, the service's `cameraOff` parameters and the skipped specs so flipping it restores the feature, and keep README/CHANGELOG silent on it. (Per-channel dialing)
- The caller ID (`useCallerIdStore`, localStorage `dialer_caller_id`) reaches `dial()` as `from` for phone numbers only: `Dialer.tsx` gates it and `signalwire.ts:makeCall` drops it for SIP/Fabric destinations. The list is the space's numbers plus verified caller IDs (`GET /api/caller-ids`), never free text. (Caller ID)
- Never use the bare word `container` anywhere in `frontend/src`, comments included. (Styling)
- Colors, fonts and radii come from the semantic tokens in `globals.css` (`bg-surface`, `text-muted`, `border-edge`, `bg-accent`, `font-display`, `font-mono`, …); no raw palette utilities (`bg-white/x`, `text-gray-x`, `emerald-*`, …) in components. (Styling)
- The Appearance setting is applied by `services/theme.ts`'s `applyTheme()`, never through `applySettings()`. (Styling)
- Preserve each file's line endings; the original files are CRLF. (Conventions)
- After editing `signalwire.ts` or `useCallStore.ts`, restart the dev server before trusting a failing Playwright run. (Testing)
- Change frontend dependencies with `npx npm@11 install ...`, not npm 10. (Environment)
- Changes to call-end, mute, reattach, screen share, hold/transfer or remote audio need a real-call test; the e2e suite drives stubs. (Testing)
- README edits stay customer-facing; fork history goes to `CHANGELOG.md`. (Conventions)
- Workbench panes are `role="region"`, never `useDialog`; keep `WORKBENCH_QUERY` and the `#root` cap in `globals.css` on the same 1024px bound. (Workbench)
- Inspector tabs are Quality · Events · Devices · Diagnostics, and tab names stay unique on the page: the workbench and screenshot specs select tabs by name without scoping. (Workbench)
- `AppBar` is the only `glass-bar pt-safe` element on the phone layout; the a11y spec counts it. (Top bar)
- Keys are `keypad-grid` + `key-button`; the digit keeps `dial-button-number` (the dialer spec reads it). No round `dial-button`. (Styling)
- The theme default is `dark`; a spec that needs `system` seeds `dialer_settings` first. (Styling)
- The event log is `logEvent()` → `getEventLog$()` only: never through `useCallStore`, never through `log.*`. (Event log)
- Failed backend requests get their copy from `describeFetchError` in `services/api.ts`, not `err.message`. (Conventions)

```bash

npm install

```

## Environment

`backend/.env` is the only env file. It holds `SPACE_NAME` (the space's full hostname), `PROJECT_ID`, `AUTH_TOKEN` (a Dashboard API token; every Fabric REST endpoint the backend calls accepts the Voice, Messaging, Fax or Video scope, and the caller ID listing also needs Numbers for the phone numbers and Voice for the verified caller IDs), `PORT`, `FRONTEND_URL`, `DIALER_API_KEY` and `FLASK_DEBUG` (leave it off: the Werkzeug debugger allows code execution and the server binds `0.0.0.0`). `vite.config.ts` loads the same file: `FRONTEND_URL`'s hostname goes into `allowedHosts` (ngrok/tunneled dev) and `DIALER_API_KEY` is baked into the bundle via `define` as `import.meta.env.VITE_DIALER_API_KEY`. There is no `frontend/.env`; restart `npm run dev` after changing the key. The key ships in the public bundle, so it is a bot deterrent paired with the rate limit, not a secret.

Vite 8 requires Node 20.19+. npm 10.8.x (what the devcontainer ships) crashes with `Cannot read properties of null (reading 'edgesOut')` when *changing* frontend dependencies (an arborist peer-set bug triggered by `@vitejs/plugin-react`'s optional peers); run those installs with `npx npm@11 install ...`. A plain `npm install`/`npm ci` from the existing lockfile works on 10.8.

`.devcontainer/` (Python 3.12 + Node 20, forwards :5001/:5173) runs `post-create.sh`, which creates the venv and runs `npm install`; `backend/.env` must still be created by hand.

Devcontainer quirks (observed 2026-10-17):
- The Flask dev server runs with the reloader on; multi-file backend rewrites can crash it mid-edit. Restart it with the backend command above.
- `pkill -f 'vite'` matches and kills the shell running it; use `pkill -f 'vit[e] --host'`.
- `@playwright/test` is pinned to 1.64.1 so `npm test` reuses the Chromium already cached under `~/.npm/_npx/`. On a machine without that cache, run `npx playwright install --with-deps chromium` as CI does.
- There is no `file` command. Check a file's line endings with `grep -c $'\r' <file>` (0 means LF).
- Scripted edits of CRLF files must open them with `newline=''` (Python) or the equivalent; a text-mode read/write silently converts the whole file to LF.

## Testing

`cd frontend && npm test` runs the Playwright suite in `frontend/e2e/` (`playwright.config.ts` starts or reuses the Vite dev server; the `phone` project). It needs **no SignalWire credentials**: pages open with `?e2e=1`, a dev-server-only seam in `useSignalWire.ts` (`E2E_SEAM`, gated on `import.meta.env.DEV`) that registers the hook's callbacks on the service (`signalWireService.setCallbacks`) without calling `initialize()`. Tests then stub service methods via `page.evaluate(import('/src/services/signalwire.ts'))` (private members are reachable at runtime), fire callbacks like `s.onIncomingCall(...)`, and drive screens with `useCallStore.getState().setCallState` — see `e2e/helpers.ts`. Vite HMR timestamps modules you've just edited, so the dev server's and the test's module instances can diverge: after editing `signalwire.ts`/`useCallStore.ts`, restart the dev server before trusting a failing run.

Specs: `dialer` (keypad, address field, Enter/Escape, last-destination redial, the stale-handler regression, the Video toggle's channel rewrite in both directions, typed channels, the phone lockout and the `withChannel` truth table, the caller ID picker: pick, phone-number-only lockout, persistence, error and partial states, the 320px fit), `suggestions` (the address field's listbox: Recents matches, arrow keys, Enter fills without dialing, Escape, click), `resources` (Directory tab, REST tabs, Recents, the search fields), `subscribers` (panel rows, Audio/Video/Switch), `settings` (live settings, connection test, the PSTN codec note, DND, device notices), `stats` (audio meter, stats sheet, health issues, badge), `events` (the Events section: rows, kind filter, copy, clear), `recovery` (media loss vs. call end, grace window, SDK-side `destroyed`, the preflight adoption guard), `a11y` (manifest, dialogs, live region, incoming-call keys), `workbench` (the `desktop` project at 1280×800: panes, no panel buttons in the bar, a Directory pick fills the field, the identity chip, the Quality tab following a call and keeping its numbers, Events, Hold/Share in the toolbar (Transfer hidden), folding a pane to its rail across a reload, the History button selecting Recents, the Devices tab's audio-processing switches, the Caller ID sheet handing focus back to the address field), `screens` (the `shots` project: non-asserting screenshots of every screen at four viewports → `e2e/screenshots/`, gitignored; the desktop viewport walks the workbench's tabs instead of the header panels). `npm test` runs the `phone` and `desktop` projects. The fake SDK directory (`FAKE_DIRECTORY`) and the stats stubs (`STATS_STUBS`) live in `e2e/helpers.ts` so the phone and desktop specs share them. The module-divergence warning above applies more widely than the two files it names: a run where every stub silently has no effect (an empty `__log`, the fake directory never appearing) means the dev server's module graph and the test's dynamic import have diverged; restart the dev server before reading anything into the failures (observed 2026-10-18 after editing `useSignalWire.ts` and components). The dev server runs React in StrictMode, which mounts effects twice: a component that fetches on mount fires two requests and keeps the second, so a `page.route` stub meant to fail "once" is consumed by the discarded first fetch — stub by a flag the test flips instead (the caller ID picker's Retry test; observed 2026-10-19).

Backend: `python -m pytest backend/tests`. `test_numbers.py` and `e2e/dialer.spec.ts` share `frontend/e2e/fixtures/dial-normalization.json`, so a change to number normalization on one side fails the other side's test until it's mirrored. `test_auth.py`/`test_listings.py` drive the Flask test client with fakes bound into each blueprint's namespace (`monkeypatch.setattr(api.auth, 'get_client', ...)`), resetting `utils.security._buckets` and the listing caches per test; they cover the gate on every route, subscriber resolution and paging bounds. `test_caller_ids.py` covers the merged caller ID listing (trimming, sorting, the unverified filter, partial and total failure, caching only complete results, the Relay URLs).

CI (`.github/workflows/ci.yml`): `npm ci`, lint, `tsc --noEmit`, build, Playwright (Chromium, traces uploaded on failure), then `py_compile` and pytest.

The e2e suite drives stubs. Anything touching call-end detection, mute, reattach, screen share, hold/transfer or remote audio needs a real call (browser-to-browser via two subscribers, a SWML script, or PSTN); the "Verified" notes below record what has been tested that way.

## Architecture notes that aren't obvious from the file tree

### Token lifecycle
Backend `/api/auth/token` and `/api/auth/refresh` both call `SignalWireClient.create_subscriber_token` — refresh just mints a fresh one (1-hour TTL). The frontend never stores tokens: `signalwire.ts` passes a `credentialProvider` with `authenticate`/`refresh` callbacks to `new SignalWire(...)`, and the SDK calls them on demand (~80% of TTL). The backend mints a **plain SAT** (no `sat:refresh` scope, no DPoP fingerprint), so the SDK relies on our `refresh()` callback rather than the Client Bound SAT path — expected. `signalwire.ts` subscribes to `client.warnings$` (added in `4.0.0-rc.0`): `credential_refresh_fallback`/`credential_no_refresh_handler` there mean refresh isn't wired correctly; `credential_no_refresh_handler` and refresh failures are escalated to the error banner with a reload prompt. (Optional hardening: forward `AuthenticateContext.fingerprint` from `authenticate(context)` to the backend with `scope: "sat:refresh"` to enable Client Bound SAT refresh.)

The default identity is the reference `swdialer` (`auth.py`'s `_TOKEN_REFERENCE`); SignalWire creates or reuses a subscriber per reference. A client-chosen subscriber is accepted **only by id**, validated against `api/subscribers.py`'s `get_subscribers_cached()` and mapped back to that subscriber's email as the reference (`_resolve_reference`) — never a raw client-supplied reference, which would reopen the IDOR the fixed reference closed. If the listing fails, a *requested* id answers 503 "Subscriber lookup unavailable" (transient; the frontend forgets a saved subscriber only on a 400 "Unknown subscriber"), while the default reference is minted anyway, since there the lookup only supplies the display name.

### Backend gate and rate limits
`utils/security.gate(request, scope, limit)` checks `X-API-Key` against `DIALER_API_KEY` (fail-closed: 503 when unset, 401 when wrong) and applies a per-IP sliding-window rate limit keyed by `scope`, so one endpoint's traffic doesn't starve another's: `token` (10/min — real, billable tokens), `subscribers` (10/min — PII), `swml`/`sip`/`calls` (30/min — "load more" pages), `caller_ids` (30/min — up to two Relay REST calls per uncached request). Each listed item costs an authenticated REST call to SignalWire with the account's credentials, so ungated listings are a free amplifier against the account's API quota; gating costs the UI nothing because the axios instance (`services/api.ts`) sends `X-API-Key` on every request. `utils/security.bounded_page()` clamps `offset ≥ 0`, `1 ≤ limit ≤ 50`. Every `requests` call has a 10 s timeout, and error bodies are generic (details go to the server log, never `str(e)` to the client).

### Backend listings (subscribers, SWML scripts, SIP credentials)
`GET /api/subscribers` (`api/subscribers.py`), `GET /api/swml/scripts` (`api/swml.py`) and `GET /api/sip/credentials` (`api/sip_credentials.py`) list resources with their dialable addresses, paginated for a "load more" UI. The SWML and SIP blueprints are structurally identical and deliberately duplicated rather than sharing a base module: listing metadata is one cheap paginated call, but fetching each resource's *addresses* is a separate REST call per resource, so metadata is cached in-process for 60 s (`_scripts_meta_cache` / `_credentials_meta_cache`) while only the requested page's addresses are fetched fresh via a small `ThreadPoolExecutor`. `q` (trimmed and capped by `utils/security.query_param`) filters the cached metadata before slicing, so `total`/`has_more` describe the matches and `offset` is relative to the filtered list — the frontend's `items.length` load-more offset depends on that. `/api/subscribers` returns each subscriber's `addresses` the same way (one `GET /resources/subscribers/{id}/addresses` per subscriber), which is what lets `SubscriberPicker.tsx` offer Audio/Video *call* buttons alongside "Switch". `SignalWireClient` (`utils/signalwire.py`) walks every paginated REST endpoint through `_get_all_pages`; `utils/signalwire.get_client()` lazily builds one client and returns `None` when the env isn't configured (each endpoint then answers 500).

### Directory tab
The resources panel's first tab is the signed-in subscriber's own address book from the SDK (`client.directory$` → `DirectoryAddressList.tsx`): every `Address` this identity can dial — other subscribers (`/private/<name>`), video rooms (where screen share is available), SIP endpoints (`call`), SWML scripts (`app`) — with a type badge and filter, and your own address marked "(you)" and not dialable (`getOwnAddressIds()` from `client.user.addresses`, plus a `resourceId` match against the token's subscriber id). Measured 2026-10-17 on a space dominated by SWML scripts (`GET /api/fabric/addresses` with a subscriber SAT): 387 addresses — 365 `app`, 17 `call`, 3 `room`, 2 `subscriber` — which the SDK pages **100 at a time, sorted by name, with no server-side type filter** (`?type=subscriber` exists on the REST endpoint but the SDK's `Directory` doesn't expose it). Apps dominate, so subscribers and rooms sit pages deep; the type filters therefore auto-`loadMore()` until `hasMore$` is false (hiding the manual button), while "All" pages manually. The tab's text search narrows the same way and shares that loop (`isNarrowing` = a chip or a non-empty query); SWML/SIP search is the backend `q` instead, and Recents filters in the browser. It deliberately doesn't use `ResourceAddressList`'s offset/limit `fetchPage`: the SDK owns the list (page 1 loads when `hasMore$` is subscribed, `loadMore()` appends, the `Directory` lives for the client's lifetime), so the component subscribes directly and renders through the shared presentational `AddressRowList`. The panel's `activeTab` is controlled by `Dialer.tsx` so other UI can open a specific tab.

### Recents
A client-side call log (`useRecentsStore.ts`, Zustand `persist` → localStorage `dialer_recents`, newest first, capped at 50): destination (the field text, `?channel=` included), display label, direction, outcome (`answered`/`missed`/`declined`/`failed`/`cancelled`), timestamps, video flag and which subscriber the browser was signed in as. Empty field + Call fills in the last outbound destination *and* its video choice; the `History` button in the address pill opens the tab. Recording happens in `useSignalWire.ts`, where direction and outcome are known: `makeCall` (start; `setCallId` once `dial()` resolves; `failed` on throw), `onIncomingCall` (start, with `from` and the call id), `onIncomingCallAutoRejected` (second call refused during a call/dial → `addFinished(..., 'missed')`, deduped per call id in the service), `onCallConnected` (`markConnected`, idempotent), the hook's `endCall` (`cancelled` if never connected — *before* the service call, whose `handleCallEnded` fires `onCallEnded` synchronously), `rejectCall` (`declined`), and `onCallEnded` (whatever is still in progress → `answered`/`missed`/`failed`). Entries left `in-progress` by a reload are settled on rehydrate. `onSelectAddress(path, video, label?)` carries the picked row's display name so the log reads "Alice", not a URL; `Dialer` keeps it only while the field still holds that destination.

### Per-channel dialing
Each address carries a `channels` map (`{audio, video, messaging}` → full dial URL, each already suffixed with the right `?channel=...`). Dialing in video mode requires the `video`-channel URL specifically, not just `{video: true}` on `dial()`: the SDK's `buildOptionsFromDestination` (rc.5) reads `?channel=` off the destination string — `video` → `{audio, video, receiveVideo: true}`, `audio` → `{audio, video: false}` — and merges it *under* the app's options, so the app's `video` wins but `receiveVideo` would otherwise stay at the preference default of `false` (a `sendonly` video offer). The **field is the dial string**: `useDialFieldStore` keeps `wantsVideo` and the text in step through `withChannel()`/`channelOf()` in `utils/address.ts`. For a Fabric address the toggle *is* the `?channel=` param — toggling rewrites it (on → `channel=video`, off → `channel=audio`, a bare address stays bare = audio), and editing the text re-derives the toggle, case-insensitively, keystroke by keystroke (so Backspace through the suffix flips it off; there is deliberately no latched state the text doesn't show). A phone number forces it off (the button is disabled with a hint); a SIP URI or an empty field keeps the user's choice and never gets a param. `selectAddress(path, video, label)` rewrites the path to the flag, so every list pick (Directory, SWML, SIP, Recents, Subscribers, suggestions, the empty-field redial, the workbench's direct store calls) lands with its channel visible, and `picked.destination` follows a toggle so the Recents label survives it. `makeCall` then only normalizes (`normalizeDestination`) and calls `client.dial(to, { audio: true, video, receiveVideo: video })`; Recents stores the field text (the auto-label drops the query via `dialPath`). Until 2026-10-19 the service appended `?channel=video` to every destination — phone numbers included — only when the toggle was on, so a video address toggled off still negotiated receive-only video, and nothing showed the rewrite. `DialableResourcesPanel.tsx` is a four-tab picker (Directory / Recents / SWML / SIP) behind a toggle in `Dialer.tsx`'s header; the SWML and SIP tabs delegate list/pagination/row UI to the resource-agnostic `ResourceAddressList.tsx` (a `fetchPage`/`getRowLabel` pair per tab), and the shared `DialButtons` component renders the Audio/Video pair everywhere (Directory, SWML, SIP, Recents, Subscribers). **Joining with the camera off is built but hidden.** `useDialFieldStore.cameraOff` is a send-side choice: a camera button that takes **From**'s slot in the dial row while Video is on (caller ID is phone-only, video never is), never touching the field text and ignored while Video is off. `makeCall`/`answerCall` then pass `video: false, receiveVideo: true` (the app's `video` wins over `?channel=video`), so the camera is never opened, and the store starts with `isVideoCall: true, isCameraOn: false`. The in-call Camera button then takes `toggleCamera`'s no-local-track branch, `self.addVideoInputDevice()`. On rc.5 that works on an answered call but not on one this browser dialed: the SDK creates the re-offer adding the camera and sets it locally, the peer connection stays in `have-local-offer` with the SDK's `isNegotiating` stuck true, no `verto.modify` is ever sent, and the far end gets no video (observed 2026-10-20 in a room and 1:1, Chromium 156). Chromium ignores the ICE restart the SDK forces on every re-offer when the connection has a candidate pool, which the SDK configures (`iceCandidatePoolSize: 10`), and the SDK waits for an ICE gathering change that never comes. So the button renders only when `SHOW_CAMERA_OFF_JOIN` (`false`, in `useDialFieldStore.ts`) is on, and `Dialer.tsx` and `useSignalWire.answerCall` ignore `cameraOff` while it is off. To restore: flip the flag, un-skip the four camera-off tests in `dialer.spec.ts` and drop its hidden-toggle test, and add the README rows and a CHANGELOG entry. Don't paper over it by dialing with video and muting: it stays hidden until the SDK is fixed. Video is disabled unless a distinct `video` channel URL exists (Recents: unless the destination is a phone number; its buttons run the entry through `withChannel`). Selecting either calls `onSelectAddress(path, video)` — it does not auto-dial.

### Caller ID is a dial option, not a setting
SignalWire accepts as the caller ID of a call to a phone number only a number the project owns or an external number it has verified, so the picker (`CallerIdSheet.tsx`, opened from the **From** button in `Dialer.tsx`'s dial row, beside Video and locked out the opposite way: for SIP/Fabric addresses) lists exactly those and has no free-text entry. `GET /api/caller-ids` (`api/caller_ids.py`) merges `GET /api/relay/rest/phone_numbers` (API token scope **Numbers**) and `GET /api/relay/rest/verified_caller_ids` (**Voice**; `verified: true` only) through `SignalWireClient.relay_api_base` — the Fabric `api_base` doesn't serve them — trimmed to `{id, number, name, kind}`, unpaged (no per-item cost, and the picker wants everything), and caches only a complete result for 60 s so a source that failed (named in `failed`; the other still lists) is retried on the next request. The choice lives in `useCallerIdStore` (Zustand `persist`, localStorage `dialer_caller_id`, number plus name for the button label), not in `DialerSettings` (those are pushed into the SDK by `applySettings()`; this one is read at dial time) and not in `useDialFieldStore` (unpersisted, cleared on call end). `Dialer.tsx` passes it as `from` only when the field holds a phone number and stores it as `outboundCallerId` for the call card's "From" line; `useSignalWire.makeCall` forwards it to the backend's dial log, and `signalwire.ts:makeCall` drops it again for SIP/Fabric destinations and omits the key when unset, so the invite is unchanged. The SDK's public `DialOptions` doesn't declare `from`; `CallOptions` does, and `dial()` spreads its options into the call session whose `from` becomes the invite's `caller_id_number` (rc.5 `dialogParams`), hence `OutboundDialOptions = DialOptions & Pick<CallOptions, 'from' | 'fromName'>`. **Observed 2026-10-19 (rc.5): on a direct subscriber → PSTN dial the platform does not use it.** The invite carries the chosen `caller_id_number`, but the PSTN leg went out from a different number the project owns (the same "a number from your account" default the SIP-credential docs describe for an unset Send As). Nothing documented lets a subscriber choose it: the subscriber resource has no Send As field. The way to control the carrier leg's caller id from a browser call is a SWML script whose `connect` sets `from` from a user variable, dialed with `userVariables` (public on `DialOptions`; query-string variables on the destination merge into it) — not built; the picker currently sets only the WebRTC leg's caller id.

### Call state is split across three places, deliberately
- `SignalWireService` (`frontend/src/services/signalwire.ts`) owns the SDK `Call` objects. It distinguishes `pendingCall` (ringing, not yet answered) from `currentCall` (active). Incoming calls that arrive while `currentCall` is set are auto-rejected.
- `useCallStore` (Zustand) holds UI state — `isInCall`, `isIncoming`, `callStatus`, mute/speaker flags.
- `useSignalWire` is the bridge: it wires SDK callbacks (`onIncomingCall`, `onCallEnded`, `onCallConnected`) into store updates.

### High-frequency observables bypass the store
`useCallStore` is for low-frequency, multi-consumer state (callbacks from `initialize()` → `setCallState`). Anything that ticks fast with one transient consumer — `networkMetrics$` (1 Hz), `getStats()` polling, `localAudioLevel$` and the remote meter's `level$` (~30 fps) — is read by the consuming component straight from a service passthrough getter (`getNetworkMetrics$()`, `getLocalAudioLevel$()`, …, the `DevicePicker` pattern) and never routed through `setCallState`, which would re-run every selector subscriber on each tick. `CallStatsSheet.tsx` (opened from the quality badge or the More sheet; polls `getConnectionStats()` for the selected ICE candidate pair and negotiated codecs) and `AudioLevelMeter.tsx` (writes `scaleX()` to the DOM directly) follow this. `networkMetrics$` emits a 30-sample ring buffer, RTT and jitter already in ms, cumulative packet counters. Sheets share `SheetPrimitives.tsx` (`SheetShell`/`SheetRow`/`SheetSwitch`/`SheetStat`/`SheetSection`). Caveat to verify on a real call: subscribing to `localAudioLevel$` "engages the local audio pipeline", after which the sender carries a processed track — `applyMicMute()` disables both the `localStream` track and the sender track, so mute should still hold.

### Call quality vs. health
The stats sheet's **Quality** row is the SDK's MOS (`qualityLevel$`/`qualityScore$`: an E-model score from the latest sample's RTT, audio jitter and *cumulative* loss; ≥4.0 excellent, ≥3.5 good, ≥3.0 fair, ≥2.0 poor). **Health** is the SDK's issue detector (`networkIssues$`; `isNetworkHealthy$` is "the list is empty"): `no_inbound_audio` (2 s without an audio packet-count change), `no_inbound_video` (3 s), `high_rtt`/`high_jitter` (×3/×5 and ×4 the average of the first 10 samples), `high_packet_loss` (>5%/10% in the last one-second interval). They legitimately disagree — a quiet baseline turns a small absolute change into a "spike" — so the sheet lists the active issues under Health. But rc.5's `RTCStatsMonitor` also tracks inbound video by *changes* in the video packet count from 0, so on any call without an inbound video track it reports a permanent `no_inbound_video` warning: `isNetworkHealthy$` false and the badge's triangle lit on every voice call. `relevantIssues()` in `signalwire.ts` drops that issue while `remoteHasVideo` (set in `handleRemoteMedia`, cleared per call) is false; both the store's `networkIssueCount` and `getNetworkIssues$()`/`getIsNetworkHealthy$()` (high-frequency passthroughs for the sheet) go through it. It's an SDK bug (skip the video check when the peer connection has no video receiver) — report it upstream rather than widening the filter.

### The SignalWire singleton must outlive React unmounts
`useSignalWire`'s cleanup deliberately does **not** call `signalWireService.disconnect()` — only `App.tsx`'s `beforeunload` listener does. React StrictMode / re-renders would otherwise tear down the registration mid-call. To "reset" the SDK, reload the page; don't try to re-initialize.

### Call reattach is enabled, and that constrains `beforeunload`
`new SignalWire(...)` passes `reconnectAttachedCalls: true`, so the SDK records each active call in `sessionStorage` and replays those records as `verto.invite` with `reattaching: true` on the next `init()` — this is what carries a live call across a page reload or WebSocket reconnect. Three things hang together: (1) `App.tsx`'s `beforeunload` listener skips `disconnect()` while `signalWireService.hasActiveCall()` — `client.disconnect()` clears the session's resume state *and* its attach records together, so disconnecting would leave the reloaded page nothing to reattach to; the cost is that closing a tab mid-call no longer hangs up, and the far end waits for the server to time the media out. (2) Reattached calls are pushed straight into `session.calls$`, bypassing both `dial()` and `incomingCalls$`, so `signalwire.ts` subscribes to `calls$` and adopts any untracked non-terminal call into `currentCall` (`adoptUntrackedCall()`, guarded by `isDialing`, since `dial()` also lands in `calls$` before it resolves, and by `preflightInProgress`, since `client.preflight()`'s media test dials through the client too — without that guard the test call took over the call screen, which unmounted the Diagnostics panel and lost the result, and the screen stayed up after the runner hung up because only `destroyed` is emitted; observed 2026-10-18). (3) `persistSession` is deliberately off — see the comment at the `new SignalWire(...)` call; it would also break `switchSubscriber()`. The SDK's JSDoc on `AttachManager.reattachCalls()` says the server rejects reattach with `INVALID_CALL_REFERENCE` pending a FreeSWITCH fix, but **verified 2026-10-17 (rc.5): a reload mid-call to a SWML script reattached** — the page came back on the call screen, `connected`, with media flowing. Failures are handled gracefully (records dropped, UI stays on the dialer). Chromium exempts pages with an active microphone capture from autoplay blocking, so a reattach in Chrome/Edge plays audio without a gesture and "Tap to enable audio" never shows there; Safari's policy differs.

### Remote audio has a fallback path
`remoteStream$` from the SDK isn't always reliable, so `setupRemoteAudioFallback` polls `call.rtcPeerConnection` and attaches a `track` listener directly. Both paths feed `handleRemoteMedia`: a stream with video goes to the remote `<video>` element (which then also plays the audio, so the audio sink is cleared), and audio-only goes to `playRemoteStream`, which renders into a single `<audio id="sw-remote-audio">` appended to `document.body` (skipping tracks it's already playing — both paths deliver the same track in different `MediaStream` wrappers).

The speaker bar is not the SDK's `remoteAudioLevel$`. On rc.5 that observable emits 0 for the whole call — `RemoteAudioMeter.setStream()` in `dist/index.mjs` creates its `MediaStreamAudioSourceNode` but never connects it to its `AnalyserNode`, and never resumes its `AudioContext` — and it is fed only by the SDK's `remoteStream$`, never by the fallback above. `services/remoteAudioMeter.ts` meters the stream `handleRemoteMedia` routes to the sink instead: a `MediaStreamAudioSourceNode` → `AnalyserNode` tap on the tone service's shared `AudioContext` (`toneService.getAudioContext()`, the one `primeOnFirstGesture()` and `resumeRemoteAudio()` resume, so a reattached call's meter starts on the same gesture that unblocks its audio), nothing connected to the destination (the sink element stays the only thing playing the audio), the SDK's analyser settings and RMS so the two bars read alike, deduped by audio track id (both delivery paths hand over the same track in different `MediaStream` wrappers), a stream without audio tracks ignored (the fallback's `track` listener can wrap a video track alone), detached in `handleCallEnded()`. `getRemoteAudioLevel$()` returns its `level$`, so the SDK's meter and its extra `AudioContext` are never instantiated. The `stats` spec drives it with an oscillator through `handleRemoteMedia`. Verified 2026-10-19 (rc.5) on a headless browser-to-browser call between the two subscribers with Chromium's fake microphone: on both sides the remote level peaked at 0.30 while the far end's own mic peaked at 0.31, the meter held exactly the track the `<audio>` sink was playing, the shared context was `running`, the speaker bar reached `scaleX(0.55)`, and both meters detached at hangup. Driving the service directly leaves the store on the dialer, so such a script must set `useCallStore`'s `isInCall`/`callStatus` itself before the bar exists.

### Call-ended detection is redundant, and media loss is not call end
The SDK's `status$` can fail to emit `disconnected` on certain failures, so the service ends a call on any of: (1) `status$` terminal (`disconnected`/`failed`/`destroyed` — the SDK's own `hangup()` emits `disconnecting` then `destroyed`, never `disconnected`, so `destroyed` is the only signal for a hang-up this app didn't start, such as the connection test's), (2) the peer connection reporting `closed` (a fallback that rarely fires: `RTCPeerConnection.close()` dispatches no state-change event), (3) a `recoveryEvent$` `max_attempts_reached`, or (4) a grace timer after ICE `disconnected`/`failed` expires with media still down. ICE `failed` alone does not end the call: the SDK's `CallRecoveryManager` (ICE restart → relay-only restart, up to `maxRecoveryAttempts`) may be recovering it, so `monitorPeerConnection` marks `isMediaDisrupted` (call screen shows "Reconnecting…", amber dot) and arms the timer instead. Two SDK facts shape this (verified in rc.5's `dist/index.mjs`): the recovery manager is driven by the stats monitor, browser `offline` events and WebSocket re-auth — **not by ICE state** — so `recoveryState$` can legitimately be `idle` while the peer connection is down (hence the timer, sized from `preferences.recoveryDebounceTime`/`maxRecoveryAttempts`/`iceRestartTimeout`, extended once if the SDK is mid-`recovering` when it fires); and `'recovering'` is in the `CallStatus` union but never emitted on `status$`. Every peer-connection handler checks it still belongs to `currentCall` and is removed in `cleanupCallSubscriptions()` — the old connection's `closed` fires after `hangup()` and must not tear down a newer call. `endCall()` eagerly calls `handleCallEnded()` before awaiting `call.hangup()`. Needs a real-call test (drop Wi‑Fi mid-call) whenever this logic changes; `e2e/recovery.spec.ts` covers the state machine with stubs.

### Mute is local, not the SDK's `self.mute()`
The server rejects `call.mute`/`call.unmute` with 403 on 1:1 calls (no `self.mute` capability), and the SDK's fallback stops the mic track and re-acquires it via `getUserMedia` on unmute — measured ~4-5 s of silence to the far end. `toggleMute()` instead records the intent in `isMicMuted` (even before the `Call` exists — Mute is live on the "Calling…" screen) and `applyMicMute()` disables both `call.localStream`'s mic track and the outgoing sender track (on answer, `localStream$` emits before the track is attached to the sender). `localStream$` re-applies it when the SDK swaps in a new mic track. `isMicMuted` is reset at the start of `makeCall()`/`answerCall()`/reattach adoption — not in `setupCallSubscriptions()`, which runs after the user may already have tapped Mute.

### The in-call timer runs from `connectedAt`, and remote audio may need a tap
`connectedAt` is set once per call in `useSignalWire`'s `onCallConnected` (`status$` re-emits `connected` after an ICE restart, which must not restart the timer). The pre-answer status line follows `call.status$` via `onCallStatusChange` (`trying`/`connecting` → "Calling…", `ringing` → "Ringing…"); the hook doesn't guess `ringing` when `dial()` resolves. DTMF is dropped until `connected` (service and keypad both gate on it). If `play()` on the remote sink is refused by the autoplay policy (no user gesture on the page yet, e.g. a call reattached after a reload), `onRemoteAudioBlocked` sets `needsAudioUnlock` and `CallScreen` shows "Tap to enable audio", which calls `resumeRemoteAudio()`. `toneService.primeOnFirstGesture()` (App.tsx) resumes the ringtone's `AudioContext` on the first pointer/keyboard gesture so a fresh tab doesn't ring silently; `DialPad` key tones use that same shared context (`toneService.playDtmf`).

### Tester settings live in `services/settings.ts`, applied without a reload
`DiagnosticsPanel.tsx` ("Diagnostics & Settings") edits `DialerSettings` — audio codec order (default PCMU, PCMA, Opus), SDK `logLevel`, `debug.logWsTraffic`, `relayOnly`, and this app's own `debugLogs` flag — persisted in localStorage `dialer_settings`. `signalwire.ts` reads them at `new SignalWire(...)` and `applySettings()` applies changes live: `setLogLevel`/`setDebugOptions` are SDK globals (immediate); `preferences.preferredAudioCodecs` and `preferences.relayOnly` are read by the SDK at each offer/answer and peer-connection creation, so they apply to the *next call* (verified in rc.5's build — no reload, unlike `switchSubscriber`). Don't enable `savePreferences`: it would persist device prefs into SDK storage and interact with `switchSubscriber()`. The panel also exposes `preflight()` options (`skipMediaTest`, `duration` in seconds) and shows the full result (STUN/TURN, media-path RTT, device checks). The media test is a real audio call the SDK's `PreflightRunner` places through `client.dial()` and hangs up itself after `duration` — or after 5 s if the far end hasn't answered, in which case only the signaling/ICE/device results come back — so `runPreflight()` sets `preflightInProgress` for the `calls$` adoption to ignore it (Reattach). Of the numbers it prints, the signaling RTT is a hard-coded 0, the media-path figure is the ICE candidate-gathering time, and download bandwidth is just the upload estimate echoed when packets arrived. Verify a codec change took by reading the codec row in the call-stats sheet.

### Do Not Disturb is `unregister()`, and the SDK can switch devices on its own
`setDoNotDisturb(true)` calls `client.unregister()` (stay connected, stop receiving calls); `isRegistered$` drives the store's `isRegistered`, the switch at the top of `SubscriberPicker.tsx`, and a `BellOff` beside the header dot — which stays green, because `ready$` is connected && authenticated and ignores registration. Session-only: every load registers again. Verified 2026-10-17 on a real browser-to-browser call: with the callee in DND the caller's `dial()` fails at the server with `422 no_devices_or_registrations` (wrapped in `CallCreateError`, whose `.error` holds the JSON-RPC error with the body); `describeCallError` maps that to "isn't online … or in Do Not Disturb". With DND off the callee rang within 2 s, and the inbound caller id arrived as `subscriber://<name>`, which `formatPhoneNumber` strips for display. `client.deviceRecovered$` (device unplugged/replugged/default changed) is surfaced through `onClientNotice` → store `clientNotice` → an info-tone `ErrorBanner` on both screens, so a user isn't left wondering why their audio moved.

### Screen share is gated on the `screenshare` capability
Per the SDK's screen-sharing guide, the control shows only when the browser has `getDisplayMedia` *and* `call.self.capabilities.screenshare$` is true. The server grants it on calls into a video room/conference and not on 1:1 calls (browser-to-browser, PSTN, SIP, SWML) — there the share leg is refused ("Must provide a participant invite first", or a 15 s `AuxiliaryLegTimeoutError`), because a share attaches to a room *participant*. (Capabilities are trustworthy for this; only `hold`/`transfer` aren't in the capability vocabulary at all.) `call.self$` is typed as `CallSelfParticipant`, which doesn't declare `capabilities`, so the code narrows with `instanceof SelfParticipant`; `distinctUntilChanged()` is needed because `self` is replaced on every `call.joined`. `describeScreenShareError()` in `useSignalWire.ts` maps the guide's error table; the sheet disables the row during `starting`/`stopping`; `toggleScreenShare(withAudio)` must run directly from the click (an `await` before `startScreenShare()` loses the user gesture for `getDisplayMedia`). `endCall()` stops an active share before `call.hangup()`: as of rc.5 `hangup()` only sends `verto.bye` for the main leg, so the share leg's "(Screen)" member otherwise lingers in the room for minutes. Verified on real room and 1:1 calls.

### Transfer and hold resolve even when the server refuses them
`call.transfer()` and `call.toggleHold()` are `verto.modify` requests; a refusal comes back nested in a successful envelope (`result.result.error`, observed as -32002 "Permission Denied." on every 1:1 transfer on rc.5), and the SDK only reports it on `call.errors$` (kind `signaling`, non-fatal). `refusalOf()` in `signalwire.ts` wraps both: `errors$` is a `ReplaySubject(1)` on the asap scheduler, so it lets the replay of the call's previous error pass before arming (otherwise an earlier DTMF/transfer failure is misattributed), runs the request, flushes once more, and returns any refusal for the caller to rethrow. Hold is purely server-side: no SDP, transceiver-direction, or `mediaDirections` change, and the SDK keeps its hold state in a private `_holdState` that it flips even when the server refuses — so the UI's `isOnHold` is optimistic (reverted on a detected refusal), and there's no client-side signal to verify it.

The transfer control itself is hidden: `SHOW_TRANSFER` (`false`) at the top of `CallScreen.tsx` gates the toolbar button, the More-sheet row and `TransferModal`, because every transfer on rc.5 was refused; `CallToolbar` and `CallControlsSheet` take `onOpenTransfer` optionally and render nothing without it. The service method, the hook's `transferCall`, the modal and `dialer.spec`'s Transfer-field test (`test.skip`) all stay, so flipping the flag (and un-skipping the test, and reverting the two `toHaveCount(0)` assertions) restores the feature. README and CHANGELOG deliberately don't describe transfer until it works — don't add a CHANGELOG entry for hiding it.

### The top bar is shared and its status pill is live
`AppBar.tsx` is the top bar of every layout: the workbench renders it once above the three panes (`Workbench.tsx`), and on phones `Dialer.tsx`, `CallScreen.tsx` and `IncomingCall.tsx` each render it themselves (`!workbench`), so exactly one exists at a time; the a11y spec counts its `glass-bar pt-safe`. It carries the wordmark (text; there is no logo asset), the connection pill (`role=status`: green, or pulsing amber "Reconnecting…" when `ready$` drops; a BellOff titled "Do Not Disturb — not receiving calls" while `isRegistered` is false), the active subscriber as a chip (`title="Signed in as X — open Subscribers"`; selects the Subscribers tab in the workbench, opens the Subscriber panel on phones), the phone layout's four panel buttons as children, and a sun/moon toggle (`desk` widths) that writes the Appearance setting through `saveSettings` + `applyTheme` and follows `<html data-theme>` with a MutationObserver so the Appearance select stays in step. There is no clock, and the quality badge is not in the bar: it lives in the call card's status strip (`CallScreen.tsx`), next to the timer and the call id (polled from `getCurrentCallId()`, copy button "Copy Call ID" — the stats sheet's has the same name and copies the same value, which `stats.spec` relies on). On tablets and narrow desktops (640–1023px, not `short` landscape phones) `globals.css` still caps `#root` to a phone-width column.

### Keys, cards and the call toolbar
`DialPad.tsx` is the 12-key pad in two modes: `dial` (hold 0 for `+`, a Delete row that clears everything when held 2 s) and `dtmf` (digits only; the in-call pad under the status strip). It no longer carries Call/End: `Dialer.tsx` renders the Video toggle (`aria-label` "Video call on/off") and the Call button in a row under the address card, and the keypad is always shown on phones but folded behind "Show keypad" in the workbench (localStorage `dialer_keypad`). `CallScreen.tsx` is one card — status strip, the always-mounted `<video>` pair in a box that is `hidden` unless `showVideoUI` (and replaced by the DTMF pad while the keypad is open), the level meters, then `CallToolbar.tsx` with every control (Mute, Keypad, Camera, Hold/Resume, Share, Speaker, More, End) on phones and desktop alike; the More sheet keeps its Hold/Share rows as well. Transfer's button, row and modal are behind `SHOW_TRANSFER` in `CallScreen.tsx` (Transfer and hold); `dialer.spec`'s Transfer-field test is `test.skip` until it's flipped. The status line is the first `aria-live="polite"` element on the phone call screen (`helpers.callStatusText` reads the first one). `IncomingCall.tsx` is a card with Decline/Accept; Enter/Escape still answer/decline.

### The desktop workbench puts panes beside the call stage, never over it
`App.tsx` renders `Workbench.tsx` when `useMediaQuery(WORKBENCH_QUERY)` is true (`(min-width: 1024px) and (min-height: 501px)`, `hooks/useMediaQuery.ts`) and the plain `Dialer` otherwise; `globals.css`'s phone-width `#root` cap stops at 1023px to match, and the `desk` raw screen in `tailwind.config.js` (`min-width: 640px and min-height: 501px`) is where the bar's panel buttons get their labels. The workbench is a flex column: `AppBar` on top, then a grid whose tracks come from the `workbench` utility, `var(--pane-left, minmax(16rem, 20rem)) minmax(0, 1fr) var(--pane-right, minmax(20rem, 24rem))`: the side panes are bounded and the center takes the rest, so the call card and its video box grow with the window. `Pane.tsx` wraps each side pane (`role="region"`); its `PaneToggle` folds it to a 2.5rem rail by setting `--pane-left`/`--pane-right` inline (`Workbench.tsx`, state persisted in localStorage `dialer_workbench`), and the pane's children stay mounted under `hidden` so the Inspector keeps its readings; `openSubscribers`/`openRecents`/`openCallStats` expand the pane they need. The center is `Dialer` unchanged — still the router to `CallScreen`/`IncomingCall`, so only one window key handler is live at a time — and it learns it is inside the workbench from `useWorkbench()` (`hooks/useWorkbench.ts`, a context the Workbench provides): no bar of its own, no panel buttons or overlays, the History button calls `openRecents()`, the keypad folds, `CallScreen` routes the quality badge and the More sheet's stats row to `openCallStats()`. The panes are `role="region"`; `useDialog` must never touch them — it moves focus inside and traps Tab, which would steal the address input's focus and Enter-to-call (the `workbench` spec asserts the input keeps focus on load).

The Inspector's tabs are Quality (`CallStatsBody`), Events (`EventLog fill`), Devices (`DeviceSections` behind a "Show devices" toggle, since it prompts for camera permission on mount, plus the three audio-processing switches, disabled with a hint until a call is up because they act on `call.self`, and the speaker-selection fact) and Diagnostics (Session facts, `DoNotDisturbSwitch`, `SettingsBody`, `ConnectionTestBody`, `ExportDiagnosticsButton`, `SdkFacts`); Diagnostics is the default, a call selects Quality and it stays there after hangup. Every panel body is a named export the pane reuses: `DestinationsTabs` (`DialableResourcesPanel.tsx`, with `subscribers` as a fifth tab rendering `SubscriberList`, and a `trailing` slot for the fold chevron), `SubscriberList`/`DoNotDisturbSwitch` (`SubscriberPicker.tsx`), `DeviceSections` (`DevicePicker.tsx`), `CallStatsBody` (`CallStatsSheet.tsx`), `SettingsBody`/`ConnectionTestBody`/`ExportDiagnosticsButton`/`SdkFacts` (`DiagnosticsPanel.tsx`). The Inspector keeps all four tab panels mounted and toggles `hidden` so the connection test keeps its result (the preflight-result loss recorded under Reattach would otherwise return) and the Quality tab keeps its last reading. `CallStatsBody` handles the service passthroughs binding to `currentCall` at subscribe time: it (re)subscribes on `callKey = connectedAt ?? (isInCall ? 0 : null)` — `isInCall` goes true before `dial()` has a Call, so the connect re-subscribes with the Call present — and on `null` it unsubscribes without clearing, which is how the numbers survive hangup. The dial field (`phoneNumber`, `wantsVideo`, `picked`) lives in `hooks/useDialFieldStore.ts` so the Destinations pane, a sibling of the call stage, fills it through the same `selectAddress`. The phone's Call Statistics panel is `SheetShell` with `anchor="top" modal={false}` (no backdrop, `aria-modal` omitted, `useDialog(..., { trapFocus: false })`) so Mute/End stay usable; on landscape phones it sits over the info column (`short:w-[calc(50%-1.5rem)]`).

### The event log is the tester's timeline
`AppEvent` (`signalwire.ts`) is `{ at, kind: 'call' | 'media' | 'client' | 'error' | 'warning' | 'user', message, detail? }` in a `ReplaySubject(200)` exposed as `getEventLog$()`; `logEvent()` is called from the subscriptions and methods the service already had: token mint/refresh, `ready$` and `isRegistered$` (both deduped, and the initial `false` is not logged), `client.errors$`/`warnings$`, `deviceRecovered$`, incoming calls (arrival, auto-reject, caller cancel), reattach adoption, `status$`, `call.errors$`, the screen-share capability grant, `networkIssues$` (each issue once as it appears and once as it clears — the SDK re-emits the list at 1 Hz), screen-share status, `recoveryState$`/`recoveryEvent$`, media disruption, ICE state (deduped per state), the peer-connection fallbacks, and the user's actions (dial, hang up, answer, decline, mute, camera, hold, transfer, screen share, audio processing, DTMF, DND, device selection, settings, preflight start/result). `handleCallEnded()` logs "Call ended" only while a call is still tracked, so the redundant end paths log once. `EventLog.tsx` subscribes directly (the log is high-frequency and single-consumer, so neither `useCallStore` nor `log.*`), filters by kind, copies the visible lines as `ISO [kind] message — detail`, and "Clear" hides what was logged so far rather than emptying the shared buffer. The `events` spec feeds the private `logEvent()` directly.

### Address suggestions come from what the browser already has
`hooks/useAddressSuggestions.ts` merges Recents (`matchesRecent`) with the Directory pages the SDK has loaded (`matchesAddress`; both in `utils/search.ts`, shared with the list search boxes), six at most, deduped by path, minus your own address and the field's exact current value. It subscribes to `directory.addresses$` only — subscribing to `hasMore$` is what triggers a fetch, and typing must not — so on phones the directory contributes once the Directory tab has been opened; on the workbench it is loaded from the start. `Dialer.tsx` owns the highlight and the keys: Up/Down cycle, Enter on a highlighted row picks (`stopPropagation` so the window Enter-to-call handler doesn't dial), Escape dismisses for the current value, and a pick dismisses for the picked value until the field changes. The input is a `combobox` with `aria-activedescendant`; options swallow mousedown so the input keeps focus through a click.

### Backend "call tracking" is a log line
The frontend fires `POST /api/calls/dial` without awaiting it — awaiting it before `client.dial()` left a window where End was a no-op and the call was placed anyway. The endpoint validates and normalizes the destination (same rules as the browser), logs it server-side and echoes a record back; nothing is stored. The real call log is the browser-side Recents store.

## Conventions

- Backend request failures are described by `describeFetchError` in `services/api.ts` (429 rate limit, 401 key rejected, 503 unconfigured with the server's own message, 500 backend-side failure, 502/504/no response "Backend unreachable"); every list, the Subscriber panel and the startup error screen use it, and the list error branches offer Retry.
- App logging goes through `frontend/src/utils/log.ts`: `log.debug`/`log.info` print only when Diagnostics & Settings → "App debug logs" is on (persisted via `services/settings.ts`), `log.warn`/`log.error` always. Don't add bare `console.*` calls; the SDK's own logging is a separate knob (`logLevel` in the same settings panel).
- Phone numbers: frontend and backend both normalize to E.164 (`+1` prefix for 10-digit US numbers; a number typed with a leading `+` keeps its digits as typed), stripping formatting characters first so a pasted `(555) 123-4567` dials. `signalwire.ts:normalizeDestination` (shared by `makeCall` and `transferCall`) and `utils/signalwire.py:format_phone_number` do this — keep them in sync, and update `frontend/e2e/fixtures/dial-normalization.json`, which both test suites read. `Dialer.tsx`'s 7-digit minimum counts digits only (`countDigits` in `utils/address.ts`).
- Dial-address detection is also duplicated, deliberately. SIP URIs (`sip:...`) and Fabric addresses (paths starting with `/`) bypass E.164 normalization entirely. Both sides check this independently: `SignalWireClient.is_dial_address` (`backend/utils/signalwire.py`) and `isDialAddress` in `frontend/src/utils/address.ts` (shared by `Dialer.tsx`'s badge/formatting and `signalwire.ts:normalizeDestination`). Same sync rule.
- Line endings are mixed and there's no `.gitattributes`. CRLF: the original files — `signalwire.ts`, `api.ts`, `tones.ts`, `useSignalWire.ts`, `useCallStore.ts`, `Dialer.tsx`, `DialPad.tsx`, `CallScreen.tsx`, `IncomingCall.tsx`, `ErrorBoundary.tsx`, `App.tsx`, `main.tsx`, `types/index.ts`, `globals.css`, `index.html`, `package.json`, the Vite/Tailwind/PostCSS/tsconfig/eslint configs, and `backend/app.py`, `api/auth.py`, `api/calls.py`, `utils/signalwire.py`, `requirements.txt`. Everything the fork added is LF, as are the docs and `.env.example`. Preserve each file's existing endings (`grep -c $'\r' <file>` tells you which it is); a text-mode rewrite turns a small edit into a whole-file diff.
- Docs have audiences. `README.md` is for SignalWire customers (setup, usage, SDK-feature-to-file map; no review-process language, no pointers to this file for architecture). `CHANGELOG.md` is the fork's history, newest first. This file is for working on the code. When you change behavior, update the README's feature map or usage if a customer would notice, and add a CHANGELOG entry.
