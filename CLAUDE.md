# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

iPhone-style web dialer using SignalWire's Fabric/WebRTC stack. It's a hands-on testing tool for the SignalWire Browser SDK, not a production app — keep that in mind when weighing hardening against convenience. Two services:

- `backend/` — Flask app on port **5001**. Mints SignalWire subscriber tokens and keeps an in-memory log of calls. It does **not** route media or signaling.
- `frontend/` — Vite + React + TypeScript on port **5173**. All WebRTC (signaling, media, DTMF) goes through the **published npm package** `@signalwire/js` (`^4.0.0-rc.5` in `frontend/package.json`, resolved to `4.0.0-rc.5` in the lockfile) directly from the browser. There is **no** local SDK alias — `vite.config.ts` resolves `@signalwire/js` from `node_modules` like any other dependency. Note: `4.0.0-rc.5` is the current npm `latest`/`rc`; there is no stable `4.0.0` yet.
- `signalwire-js/` — **not present in this checkout.** It was previously referenced as an optional local clone of the SignalWire Browser SDK monorepo, kept only for reading `examples/` (authoritative guide to the v4 API) and `packages/main/src/` (SDK source). It's never required — the dialer only ever consumes the npm package — so don't assume it exists; clone it yourself at the matching version tag if you need to read SDK internals.

## Commands

A `venv` lives at the repo root (`/venv`). Always activate it before running Python: `source venv/bin/activate`.

```bash
# Backend (from repo root)
source venv/bin/activate
cd backend && python app.py            # dev server on :5001

# Frontend
cd frontend
npm install
npm run dev                            # Vite dev server on :5173 (proxies /api → :5001)
npm run build                          # tsc + vite build
npm run lint                           # eslint
npm test                               # Playwright e2e suite (no credentials needed)
npm run test:shots                     # screenshots of every screen → e2e/screenshots/
```

Tests: `cd frontend && npm test` runs the Playwright suite in `frontend/e2e/` (`playwright.config.ts` starts or reuses the Vite dev server). It needs **no SignalWire credentials**: pages open with `?e2e=1`, a dev-server-only seam in `useSignalWire.ts` that registers the hook's callbacks on the service (`signalWireService.setCallbacks`) without calling `initialize()`. Tests then stub service methods via `page.evaluate(import('/src/services/signalwire.ts'))` (private members are reachable at runtime), fire callbacks like `s.onIncomingCall(...)`, and drive screens with `useCallStore.getState().setCallState` — see `e2e/helpers.ts`. Keep the dev server and the test's module instances in sync: Vite HMR timestamps modules you've just edited, so after editing `signalwire.ts`/`useCallStore.ts` restart the dev server before trusting a failing run. `npm run test:shots` writes non-asserting screenshots of every screen at four viewports to `e2e/screenshots/` (gitignored). Backend: `source venv/bin/activate && python -m pytest backend/tests` (install `backend/requirements-dev.txt` first); `test_numbers.py` and `e2e/dialer.spec.ts` share `frontend/e2e/fixtures/dial-normalization.json` to enforce the number-normalization sync rule below. CI (`.github/workflows/ci.yml`) runs lint, `tsc`, build, the Playwright suite and pytest.

Vite 8 requires Node 20.19+. npm 10.8.x (what the devcontainer ships) crashes with `Cannot read properties of null (reading 'edgesOut')` when *changing* frontend dependencies (an arborist peer-set bug triggered by `@vitejs/plugin-react`'s optional peers); run those installs with `npx npm@11 install ...`. A plain `npm install`/`npm ci` from the existing lockfile works fine on 10.8.

A `.devcontainer/` (Python 3.12 + Node 20, forwards :5001/:5173) is available as an alternative to manual setup — `.devcontainer/post-create.sh` creates the venv and runs `npm install` automatically.

`backend/.env` holds `SPACE_NAME`, `PROJECT_ID`, `AUTH_TOKEN`, `PORT`, `FRONTEND_URL`, and `DIALER_API_KEY`. `vite.config.ts` reads `FRONTEND_URL` from `backend/.env` to add its hostname to `allowedHosts` — useful for ngrok/tunneled dev. `frontend/.env` holds the matching `VITE_DIALER_API_KEY`.

## Architecture notes that aren't obvious from the file tree

**Token lifecycle.** Backend `/api/auth/token` and `/api/auth/refresh` both call `SignalWireClient.create_subscriber_token` — refresh just mints a fresh one. The frontend never stores tokens; instead `signalwire.ts` passes a `credentialProvider` with `authenticate`/`refresh` callbacks to `new SignalWire(...)`, and the SDK calls them on demand (~80% of TTL). Don't add token caching on the frontend. The backend mints a **plain SAT** (no `sat:refresh` scope, no DPoP fingerprint), so the SDK relies on our developer `refresh()` callback rather than the Client Bound SAT path — that's expected. `signalwire.ts` subscribes to `client.warnings$` (added in `4.0.0-rc.0`): `credential_refresh_fallback`/`credential_no_refresh_handler` warnings there are the signal that token refresh isn't wired up correctly. (Optional future hardening: forward the `AuthenticateContext.fingerprint` from `authenticate(context)` to the backend with `scope: "sat:refresh"` to enable automatic Client Bound SAT refresh.)

**Token endpoints are gated.** `auth.py`'s `_gate()` fail-closes `/api/auth/token` and `/api/auth/refresh` when `DIALER_API_KEY` is unset (they mint real, billable SignalWire tokens, so this must never be silently open), plus a 10-req/60s per-IP rate limit. The frontend sends the matching key via `X-API-Key`, read from the Vite build-time env var `VITE_DIALER_API_KEY` (`services/api.ts`). This is **not a real secret** once built — it ships inside the public JS bundle — so its actual value is raising the bar against automated bots/scanners, paired with the rate limit; it doesn't stop a targeted attacker who reads the bundle. `/api/calls/incoming` has no equivalent check — that's intentional, see "Backend call tracking is cosmetic" below. `/api/subscribers` uses the same gate (subscriber records carry PII). The resource listings (`/api/swml/scripts`, `/api/sip/credentials`) are deliberately ungated to keep testing friction low. Note the axios instance sends `X-API-Key` on every request, not just token calls.

**Dialable resources browser (SWML Scripts + SIP Credentials).** `GET /api/swml/scripts` (`backend/api/swml.py`) and `GET /api/sip/credentials` (`backend/api/sip_credentials.py`) each list an account's resources (SWML scripts / SIP credentials, i.e. `sip_endpoints`) with their dialable addresses, paginated for a "load more" UI. Both blueprints are structurally identical, deliberately duplicated rather than sharing a base module: listing resource metadata is one cheap paginated call; fetching each resource's *addresses* is a separate REST call per resource, so metadata is cached in-process for 60s (`_scripts_meta_cache` / `_credentials_meta_cache`) while only the newly-requested page's addresses are fetched fresh, via a small `ThreadPoolExecutor`. `SignalWireClient.list_swml_scripts`/`list_swml_script_addresses` and `list_sip_credentials`/`list_sip_credential_addresses` (`backend/utils/signalwire.py`) all walk their paginated REST endpoint through the shared `_get_all_pages` helper. What the blueprints *do* share: one lazily built REST client via `utils/signalwire.get_client()` (returns `None` when the env isn't configured; each endpoint answers 500), `utils/security.bounded_page()` (clamps `offset ≥ 0`, `1 ≤ limit ≤ 50` — each listed item costs a REST call), and `api/subscribers.py`'s `get_subscribers_cached()`/`display_name_for()`, which `auth.py` imports to validate a client-chosen subscriber id. Every `requests` call has a 10 s timeout, and error bodies are generic (details go to the server log, never `str(e)` to the client).

The panel's first tab, **Directory**, is different: it's the signed-in subscriber's own address book from the SDK (`client.directory$` → `DirectoryAddressList.tsx`), listing every `Address` this identity can dial — other subscribers (browser-to-browser calls, `/private/<name>`), video rooms (where screen share is available), SIP endpoints (`call`), SWML scripts (`app`) — with a type badge and type filter, and your own address marked "(you)" and not dialable. **Measured on the test space (2026-10-17, via `GET /api/fabric/addresses` with a subscriber SAT):** 387 addresses — 365 `app`, 17 `call`, 3 `room`, 2 `subscriber` — which the SDK pages **100 at a time, sorted by name, with no server-side type filter** (`?type=subscriber` exists on the REST endpoint but the SDK's `Directory` doesn't expose it). Apps dominate, so the subscribers and rooms sit two or three pages deep; that's why the type filters auto-`loadMore()` until `hasMore$` is false (and hide the manual "Load more" button), while "All" pages manually. An earlier read of only the first page wrongly concluded subscribers weren't listed. Your own address is marked (`getOwnAddressIds()` from `client.user.addresses`, plus a `resourceId` match against the token's subscriber id). It deliberately doesn't go through `ResourceAddressList`'s offset/limit `fetchPage`: the SDK owns that list (server page size, name-sorted, page 1 loads when `hasMore$` is subscribed, `loadMore()` appends, and the `Directory` lives for the client's lifetime), so the component subscribes directly and renders through the shared presentational `AddressRowList` that `ResourceAddressList` was split into. The panel's `activeTab` is controlled by `Dialer.tsx` so other UI can open a specific tab.

The **Recents** tab is a client-side call log (`useRecentsStore.ts`, Zustand `persist` → localStorage `dialer_recents`, newest first, capped at 50): destination, display label, direction, outcome (`answered`/`missed`/`declined`/`failed`/`cancelled`), timestamps, video flag and which subscriber the browser was signed in as. It replaced the single `lastDialedNumber`: empty field + Call fills in the last outbound destination *and* its video choice, and the `History` button in the address pill opens the tab. Recording happens in `useSignalWire.ts` — the bridge is where direction and outcome are already known — at `makeCall` (start; `setCallId` once `dial()` resolves; `failed` on throw), `onIncomingCall` (start, now also given `from` and the call id), `onIncomingCallAutoRejected` (a new service callback for the second call refused during a call/dial → `addFinished(..., 'missed')`, deduped per call id in the service), `onCallConnected` (`markConnected`, idempotent), the hook's `endCall` (`cancelled` if never connected — *before* the service call, whose `handleCallEnded` fires `onCallEnded` synchronously), `rejectCall` (`declined`), and `onCallEnded` (whatever is still in progress → `answered`/`missed`/`failed`). Entries left `in-progress` by a reload are settled on rehydrate. `onSelectAddress(path, video, label?)` now carries the picked row's display name so the log reads "Alice", not a URL; `Dialer` keeps it only while the field still holds that destination. The backend `/api/calls/dial` post stays fire-and-forget and cosmetic.

Each address carries a `channels` map (`{audio, video, messaging}` → full dial URL, each already suffixed with the right `?channel=...` query string) — dialing the platform in video mode requires using the `video`-channel URL specifically, not just passing `{video: true}` to the SDK's `dial()` call. On the frontend, `DialableResourcesPanel.tsx` renders a two-tab picker (SWML Scripts / SIP Credentials) behind a toggle in `Dialer.tsx`'s header, delegating the actual list/pagination/row UI to the shared, resource-agnostic `ResourceAddressList.tsx` (parameterized by a `fetchPage`/`getRowLabel` pair per tab). Each address row shows labeled Audio and Video buttons; Video is disabled unless a distinct `video` channel URL exists. Selecting either calls `onSelectAddress(path, video)`, which `Dialer.tsx` uses to both fill the dial-pad input and sync the existing `wantsVideo` toggle (so the SDK's local media negotiation matches the channel that was actually selected) — it does not auto-dial.

**Call state is split across three places, deliberately:**
- `SignalWireService` (`frontend/src/services/signalwire.ts`) owns the SDK `Call` objects. It distinguishes `pendingCall` (ringing, not yet answered) from `currentCall` (active). Incoming calls that arrive while `currentCall` is set are auto-rejected.
- `useCallStore` (Zustand) holds UI state — `isInCall`, `isIncoming`, `callStatus`, mute/speaker flags.
- `useSignalWire` is the bridge: it wires SDK callbacks (`onIncomingCall`, `onCallEnded`, `onCallConnected`) into store updates.

**High-frequency SDK observables bypass the store.** `useCallStore` is for low-frequency, multi-consumer state (callbacks from `initialize()` → `setCallState`). Anything that ticks fast and has one transient consumer — `networkMetrics$` (1 Hz), `getStats()` polling, `localAudioLevel$`/`remoteAudioLevel$` (~30 fps) — is read by the consuming component straight from a service passthrough getter (`getNetworkMetrics$()`, `getLocalAudioLevel$()`, …, the `DevicePicker` pattern) and never routed through `setCallState`, which would re-run every selector subscriber on each tick. `CallStatsSheet.tsx` (opened from the quality badge or the More sheet; polls `getConnectionStats()` for the selected ICE candidate pair and negotiated codecs) and `AudioLevelMeter.tsx` (writes `scaleX()` to the DOM directly) follow this. `networkMetrics$` emits a 30-sample ring buffer, with RTT and jitter already in ms and cumulative packet counters. Sheets share `SheetPrimitives.tsx` (`SheetShell`/`SheetRow`/`SheetSwitch`/`SheetStat`/`SheetSection`). Caveat to verify on a real call: the SDK says subscribing to `localAudioLevel$` "engages the local audio pipeline", after which the sender carries a processed track — `applyMicMute()` disables both the `localStream` track and the sender track, so mute should still hold.

**The SignalWire singleton must outlive React unmounts.** `useSignalWire`'s cleanup deliberately does **not** call `signalWireService.disconnect()` — only `App.tsx`'s `beforeunload` listener does. React StrictMode / re-renders would otherwise tear down the registration mid-call. If you need to "reset" the SDK, reload the page; don't try to re-initialize.

**Call reattach is enabled, and that constrains `beforeunload`.** `new SignalWire(...)` passes `reconnectAttachedCalls: true`, so the SDK records each active call in `sessionStorage` and replays those records as `verto.invite` with `reattaching: true` on the next `init()` — this is what carries a live call across a page reload or WebSocket reconnect. Three things hang together and shouldn't be changed in isolation: (1) `App.tsx`'s `beforeunload` listener skips `disconnect()` while `signalWireService.hasActiveCall()` — `client.disconnect()` clears the session's resume state *and* its attach records together, so disconnecting would leave the reloaded page nothing to reattach to; the cost is that closing a tab mid-call no longer hangs up, and the far end waits for the server to time the media out. (2) Reattached calls are pushed straight into `session.calls$`, bypassing both `dial()` and `incomingCalls$`, so `signalwire.ts` subscribes to `calls$` and adopts any untracked non-terminal call into `currentCall` (guarded by `isDialing`, since `dial()` also lands in `calls$` before it resolves). (3) `persistSession` is deliberately left off — see the comment at the `new SignalWire(...)` call for why, and note it would break `switchSubscriber()`. The SDK's own JSDoc on `AttachManager.reattachCalls()` says the server rejects reattach with `INVALID_CALL_REFERENCE` pending a FreeSWITCH fix, but **on 2026-10-17 a real test (reload mid-call to a SWML script, rc.5) reattached successfully**: the reloaded page came back on the call screen, `connected`, with media flowing. Failures are still handled gracefully (records dropped, UI stays on the dialer). Note for manual testing of the "Tap to enable audio" path: Chromium exempts pages with an active microphone capture from autoplay blocking, so a reattach in Chrome/Edge plays audio without a gesture and the control never shows; Safari's policy differs.

**Remote audio has a fallback path.** `remoteStream$` from the SDK isn't always reliable, so `setupRemoteAudioFallback` polls `call.rtcPeerConnection` and attaches a `track` listener directly. Both paths feed `handleRemoteMedia`: a stream with video goes to the remote `<video>` element (which then also plays the audio, so the audio sink is cleared), and audio-only goes to `playRemoteStream`, which renders into a single `<audio id="sw-remote-audio">` element appended to `document.body` (and skips re-assigning tracks it's already playing — both paths deliver the same track in different `MediaStream` wrappers). Don't remove the fallback without verifying audio still works on both inbound and outbound calls.

**Call-ended detection is redundant, and media loss is not call end.** The SDK's `status$` can fail to emit `disconnected` on certain failures, so the service ends a call on any of: (1) `status$` terminal (`disconnected`/`failed`), (2) the peer connection reaching `closed` (only the SDK's own destroy produces it), (3) a `recoveryEvent$` `max_attempts_reached`, or (4) a grace timer after ICE `disconnected`/`failed` expires with media still down. ICE `failed` alone no longer ends the call: the SDK's `CallRecoveryManager` (ICE restart → relay-only restart, up to `maxRecoveryAttempts`) may be recovering it, so `monitorPeerConnection` marks `isMediaDisrupted` (call screen shows "Reconnecting…", amber dot) and arms the timer instead. Two SDK facts shape this (verified in rc.5's `dist/index.mjs`): the recovery manager is driven by the stats monitor, browser `offline` events and WebSocket re-auth — **not by ICE state** — so `recoveryState$` can legitimately be `idle` while the peer connection is down (hence the timer, sized from `preferences.recoveryDebounceTime`/`maxRecoveryAttempts`/`iceRestartTimeout`, extended once if the SDK is mid-`recovering` when it fires); and `'recovering'` is in the `CallStatus` union but never emitted on `status$`. Every peer-connection handler checks it still belongs to `currentCall` and is removed in `cleanupCallSubscriptions()` — the old connection's `closed` fires after `hangup()` and must not tear down a newer call. `endCall()` eagerly calls `handleCallEnded()` before awaiting `call.hangup()` — don't reorder. Needs a real-call test (drop Wi‑Fi mid-call) whenever this logic changes.

**Mute is local, not the SDK's `self.mute()`.** The server rejects `call.mute`/`call.unmute` with 403 on 1:1 calls (no `self.mute` capability), and the SDK's fallback stops the mic track and re-acquires it via `getUserMedia` on unmute — measured ~4-5s of silence to the far end. `toggleMute()` instead records the intent in `isMicMuted` (even before the `Call` exists — Mute is live on the "Calling…" screen) and `applyMicMute()` disables both `call.localStream`'s mic track and the outgoing sender track (on answer, `localStream$` emits before the track is attached to the sender). `localStream$` re-applies it when the SDK swaps in a new mic track. `isMicMuted` is reset at the start of `makeCall()`/`answerCall()`/reattach adoption — not in `setupCallSubscriptions()`, which runs after the user may already have tapped Mute.

**The in-call timer runs from `connectedAt`, and remote audio may need a tap.** `connectedAt` is set once per call in `useSignalWire`'s `onCallConnected` (`status$` re-emits `connected` after an ICE restart, which must not restart the timer), and the pre-answer status line follows `call.status$` via `onCallStatusChange` (`trying`/`connecting` → "Calling…", `ringing` → "Ringing…"); the hook no longer guesses `ringing` when `dial()` resolves. DTMF is dropped until `connected` (service and keypad both gate on it). If `play()` on the remote sink is refused by the autoplay policy — no user gesture on the page yet, e.g. a call reattached after a reload — `onRemoteAudioBlocked` sets `needsAudioUnlock` and `CallScreen` shows "Tap to enable audio", which calls `resumeRemoteAudio()`. `toneService.primeOnFirstGesture()` (App.tsx) resumes the ringtone's `AudioContext` on the first pointer/keyboard gesture so a fresh tab doesn't ring silently; `DialPad` key tones use that same shared context (`toneService.playDtmf`).

**Tester settings live in `services/settings.ts`, applied without a reload.** `DiagnosticsPanel.tsx` ("Diagnostics & Settings") edits `DialerSettings` — audio codec order (default PCMU, PCMA, Opus = the old hardcoded G.711 preference), SDK `logLevel`, `debug.logWsTraffic`, `relayOnly`, and this app's own `debugLogs` flag — persisted in localStorage `dialer_settings`. `signalwire.ts` reads them at `new SignalWire(...)` and `applySettings()` applies changes live: `setLogLevel`/`setDebugOptions` are SDK globals (immediate); `preferences.preferredAudioCodecs` and `preferences.relayOnly` are read by the SDK at each offer/answer and peer-connection creation, so they apply to the *next call* (verified in rc.5's build — no reload, unlike `switchSubscriber`). Don't enable `savePreferences`: it would persist device prefs into SDK storage and interact with `switchSubscriber()`. The panel also exposes `preflight()` options (`skipMediaTest`, `duration` in seconds) and shows the full result (STUN/TURN, media-path RTT, device checks). Verify a codec change took by reading the codec row in the call-stats sheet.

**Do Not Disturb is `unregister()`, and the SDK can switch devices on its own.** `setDoNotDisturb(true)` calls `client.unregister()` (stay connected, stop receiving calls); `isRegistered$` drives the store's `isRegistered`, the switch at the top of `SubscriberPicker.tsx`, and a `BellOff` beside the header dot — which stays green, because `ready$` is connected && authenticated and ignores registration. Session-only: every load registers again. Verified on a real browser-to-browser call (2026-10-17): with the callee in DND the caller's `dial()` fails at the server with `422 no_devices_or_registrations` (wrapped in `CallCreateError`, whose `.error` holds the JSON-RPC error with the body); `describeCallError` maps that to "isn't online … or in Do Not Disturb". With DND off the callee rang within 2 s, and the inbound caller id arrived as `subscriber://<name>`, which `formatPhoneNumber` strips for display. `client.deviceRecovered$` (device unplugged/replugged/default changed) is surfaced through `onClientNotice` → store `clientNotice` → an info-tone `ErrorBanner` on both screens, so a user isn't left wondering why their audio moved.

**Screen share is gated on the `screenshare` capability, per the SDK's screen-sharing guide.** The control shows only when the browser has `getDisplayMedia` *and* `call.self.capabilities.screenshare$` is true. The server grants it on calls into a video room/conference and not on 1:1 calls (browser-to-browser, PSTN, SIP, SWML) — there the share leg is refused ("Must provide a participant invite first", or a 15s `AuxiliaryLegTimeoutError`), because a share attaches to a room *participant*. (Capabilities *are* trustworthy for this; only `hold`/`transfer` aren't in the capability vocabulary at all.) `call.self$` is typed as `CallSelfParticipant`, which doesn't declare `capabilities`, so the code narrows with `instanceof SelfParticipant`; `distinctUntilChanged()` is needed because `self` is replaced on every `call.joined`. `describeScreenShareError()` in `useSignalWire.ts` maps the guide's error table; the sheet disables the row during `starting`/`stopping`; `toggleScreenShare(withAudio)` must run directly from the click (no `await` before `startScreenShare()`, or `getDisplayMedia` loses the user gesture). **`endCall()` stops an active share before `call.hangup()`:** as of 4.0.0-rc.5 `hangup()` only sends `verto.bye` for the main leg, so the share leg's "(Screen)" member otherwise lingers in the room for minutes. Verified on real room and 1:1 calls.

**`call.transfer()` and `call.toggleHold()` resolve even when the server refuses them.** Both are `verto.modify` requests; a refusal comes back nested in a successful envelope (`result.result.error`, observed as -32002 "Permission Denied." on every 1:1 transfer on 4.0.0-rc.5), and the SDK only reports it on `call.errors$` (kind `signaling`, non-fatal). `refusalOf()` in `signalwire.ts` wraps both: `errors$` is a `ReplaySubject(1)` on the asap scheduler, so it lets the replay of the call's previous error pass before arming (otherwise an earlier DTMF/transfer failure is misattributed), runs the request, flushes once more, and returns any refusal for the caller to rethrow. Don't simplify this back to a bare `await call.transfer()`/`toggleHold()`. Hold is purely server-side: no SDP, transceiver-direction, or `mediaDirections` change, and the SDK keeps its hold state in a private `_holdState` that it flips even when the server refuses — so the UI's `isOnHold` is optimistic (reverted on a detected refusal), and there's no client-side signal to verify it.

**The header is shared and its status dot is live.** `StatusBar.tsx` is the top bar for both `Dialer.tsx` and `CallScreen.tsx`: the dot follows `isClientReady` (green, or pulsing amber "Reconnecting…" when `ready$` drops), and the clock ticks on the minute. On desktop/tablet `globals.css` caps `#root` to a phone-width column (not on `short` landscape phones), so the centered title is hidden whenever the bar carries the dialer's header icons except in landscape.

**Window-level key handlers filter their targets.** `Dialer.tsx`'s Enter-to-call ignores Enter from any other input/button (Enter in the Diagnostics field used to dial), and `CallScreen.tsx`'s DTMF listener ignores keys typed into fields (the Transfer destination was being sent as DTMF). Escape closes header panels, the More sheet, and the Transfer modal. Dial-pad keys `preventDefault` on mousedown so clicking them doesn't steal focus from the address input.

**Overlays share one dialog hook; the app is installable.** Every sheet, modal and header panel attaches `useDialog(isOpen, onClose)` (`frontend/src/hooks/useDialog.ts`) to its container with `role="dialog" aria-modal="true"` and a label: it moves focus inside on open (first field, else first control), keeps Tab cycling within, closes on Escape (stopping propagation so the screen-level Escape handlers in `Dialer.tsx`/`CallScreen.tsx` don't double-fire), and returns focus to the opener on close. `SheetShell` does this for every sheet; `TransferModal` passes a no-op while a transfer is in flight. Keyboard: Enter/Escape answer/decline on the incoming screen, `m` toggles mute in a call, digits send DTMF once connected, Enter dials from the address field. `index.html` links `public/manifest.webmanifest` and PNG icons (rendered from `phone.svg`), sets `theme-color`, and keeps pinch-zoom enabled; `globals.css`'s `pt-safe`/`pb-safe` utilities pad the status bar and bottom controls past the notch and home indicator when installed (`viewport-fit=cover`). The production build puts `@signalwire/js` + `rxjs` in a `vendor-signalwire` chunk (`vite.config.ts`, rolldown `codeSplitting`) — the SDK can't be lazy-loaded since startup needs it.

**Styling is Tailwind 4 with a JS config.** `globals.css` does `@import 'tailwindcss'` plus `@config '../../tailwind.config.js'`, and defines the project's custom classes (`app-shell`, `glass-*`, `dial-button*`) as `@utility` blocks. `tailwind.config.js` adds a raw `short` screen (`max-height: 500px`) used for side-by-side layouts on phones in landscape; dial-button sizes step down by viewport height in `globals.css`. Tailwind 4 emits media queries in range syntax (`(height<=500px)`), and `hover:` only applies on hover-capable devices. **Pitfall:** Tailwind scans every source file — comments and variable names included — for class candidates, and the bare word `container` anywhere in `frontend/src` makes it emit its `.container` utility, which combined with the raw `short` screen produces invalid CSS (`@media (width >= (max-height: 500px))`) and fails `npm run build` in the minifier. Name things `dialogEl`/`wrapper`/etc. instead (see `useDialog.ts`).

**Backend "call tracking" is cosmetic.** The frontend fires the `/api/calls/dial` log without awaiting it — awaiting it before `client.dial()` left a window where End was a no-op and the call was placed anyway. `active_calls`/`call_history` in `backend/api/calls.py` are module-level dicts/lists (capped at 200/100). They don't drive any SDK behavior; they exist for the optional `/api/calls/*` endpoints, which nothing in the frontend reads (`callsAPI` only has `initiateCall`). The real call log is the browser-side Recents store. Treat the backend call store as ephemeral debugging data, not source of truth. (The unused `/api/calls/incoming` webhook stub and `/api/auth/validate` placeholder were removed.)

## Conventions

- App logging goes through `frontend/src/utils/log.ts`: `log.debug`/`log.info` print only when Diagnostics & Settings → "App debug logs" is on (persisted via `services/settings.ts`), `log.warn`/`log.error` always. Don't add bare `console.*` calls; the SDK's own logging is a separate knob (`logLevel` in the same settings panel).

- The `signalwire-js/` checkout has its own `CLAUDE.md` (e.g. `signalwire-js/packages/main/CLAUDE.md`) — those rules apply when editing files **inside** `signalwire-js/`, not to the dialer code in `frontend/` and `backend/`. In practice you shouldn't be editing the SDK from this repo; consume the npm package instead.
- Phone numbers: frontend and backend both normalize to E.164 (`+1` prefix for 10-digit US numbers), stripping formatting characters first so a pasted `(555) 123-4567` dials. `signalwire.ts:normalizeDestination` (shared by `makeCall` and `transferCall`) and `utils/signalwire.py:format_phone_number` do this — keep them in sync if you change the rules. `Dialer.tsx`'s 7-digit minimum counts digits only (`countDigits` in `utils/address.ts`).
- Dial-address detection is also duplicated, deliberately. SIP URIs (`sip:...`) and Fabric addresses (paths starting with `/`) bypass E.164 normalization entirely. Both sides check this independently: `SignalWireClient.is_dial_address` (`backend/utils/signalwire.py`) and `isDialAddress` in `frontend/src/utils/address.ts` (shared by `Dialer.tsx`'s badge/formatting and `signalwire.ts:normalizeDestination`). Keep them in sync, same rule as phone-number formatting above.
- Line endings are mixed and there's no `.gitattributes`: many frontend files (e.g. `signalwire.ts`, `Dialer.tsx`, `CallScreen.tsx`, `globals.css`, `package.json`) are CRLF, others are LF. Preserve each file's existing endings — tools that read/write in text mode (e.g. Python's `open().read()`/`write()`) silently convert CRLF to LF and turn a small edit into a whole-file diff.
