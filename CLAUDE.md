# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

iPhone-style web dialer using SignalWire's Fabric/WebRTC stack. It's a hands-on testing tool for the SignalWire Browser SDK, not a production app — keep that in mind when weighing hardening against convenience. Two services:

- `backend/` — Flask app on port **5001**. Mints SignalWire subscriber tokens and keeps an in-memory log of calls. It does **not** route media or signaling.
- `frontend/` — Vite + React + TypeScript on port **5173**. All WebRTC (signaling, media, DTMF) goes through the **published npm package** `@signalwire/js` (`^4.0.0-rc.5` in `frontend/package.json`, resolved to `4.0.0-rc.5` in the lockfile) directly from the browser. There is **no** local SDK alias — `vite.config.ts` resolves `@signalwire/js` from `node_modules` like any other dependency. Note: `4.0.0-rc.5` is the current npm `latest`/`rc`; there is no stable `4.0.0` yet.
- `signalwire-js/` — **not present in this checkout.** It was previously referenced as an optional local clone of the SignalWire Browser SDK monorepo, kept only for reading `examples/` (authoritative guide to the v4 API) and `packages/main/src/` (SDK source). It's never required — the dialer only ever consumes the npm package — so don't assume it exists; clone it yourself at the matching version tag if you need to read SDK internals.

## Commands

A `venv` lives at the repo root (`/venv`). Always activate it before running Python: `source venv/bin/activate`.

```bash
# Backend (from repo root)
source venv/bin/activate
cd backend && python app.py            # dev server on :5001

# Frontend
cd frontend
npm install
npm run dev                            # Vite dev server on :5173 (proxies /api → :5001)
npm run build                          # tsc + vite build
npm run lint                           # eslint
```

There are no tests in this repo.

Vite 8 requires Node 20.19+. npm 10.8.x (what the devcontainer ships) crashes with `Cannot read properties of null (reading 'edgesOut')` when *changing* frontend dependencies (an arborist peer-set bug triggered by `@vitejs/plugin-react`'s optional peers); run those installs with `npx npm@11 install ...`. A plain `npm install`/`npm ci` from the existing lockfile works fine on 10.8.

A `.devcontainer/` (Python 3.12 + Node 20, forwards :5001/:5173) is available as an alternative to manual setup — `.devcontainer/post-create.sh` creates the venv and runs `npm install` automatically.

`backend/.env` holds `SPACE_NAME`, `PROJECT_ID`, `AUTH_TOKEN`, `PORT`, `FRONTEND_URL`, and `DIALER_API_KEY`. `vite.config.ts` reads `FRONTEND_URL` from `backend/.env` to add its hostname to `allowedHosts` — useful for ngrok/tunneled dev. `frontend/.env` holds the matching `VITE_DIALER_API_KEY`.

## Architecture notes that aren't obvious from the file tree

**Token lifecycle.** Backend `/api/auth/token` and `/api/auth/refresh` both call `SignalWireClient.create_subscriber_token` — refresh just mints a fresh one. The frontend never stores tokens; instead `signalwire.ts` passes a `credentialProvider` with `authenticate`/`refresh` callbacks to `new SignalWire(...)`, and the SDK calls them on demand (~80% of TTL). Don't add token caching on the frontend. The backend mints a **plain SAT** (no `sat:refresh` scope, no DPoP fingerprint), so the SDK relies on our developer `refresh()` callback rather than the Client Bound SAT path — that's expected. `signalwire.ts` subscribes to `client.warnings$` (added in `4.0.0-rc.0`): `credential_refresh_fallback`/`credential_no_refresh_handler` warnings there are the signal that token refresh isn't wired up correctly. (Optional future hardening: forward the `AuthenticateContext.fingerprint` from `authenticate(context)` to the backend with `scope: "sat:refresh"` to enable automatic Client Bound SAT refresh.)

**Token endpoints are gated.** `auth.py`'s `_gate()` fail-closes `/api/auth/token` and `/api/auth/refresh` when `DIALER_API_KEY` is unset (they mint real, billable SignalWire tokens, so this must never be silently open), plus a 10-req/60s per-IP rate limit. The frontend sends the matching key via `X-API-Key`, read from the Vite build-time env var `VITE_DIALER_API_KEY` (`services/api.ts`). This is **not a real secret** once built — it ships inside the public JS bundle — so its actual value is raising the bar against automated bots/scanners, paired with the rate limit; it doesn't stop a targeted attacker who reads the bundle. `/api/calls/incoming` has no equivalent check — that's intentional, see "Backend call tracking is cosmetic" below. `/api/subscribers` uses the same gate (subscriber records carry PII). The resource listings (`/api/swml/scripts`, `/api/sip/credentials`) are deliberately ungated to keep testing friction low. Note the axios instance sends `X-API-Key` on every request, not just token calls.

**Dialable resources browser (SWML Scripts + SIP Credentials).** `GET /api/swml/scripts` (`backend/api/swml.py`) and `GET /api/sip/credentials` (`backend/api/sip_credentials.py`) each list an account's resources (SWML scripts / SIP credentials, i.e. `sip_endpoints`) with their dialable addresses, paginated for a "load more" UI. Both blueprints are structurally identical, deliberately duplicated rather than sharing a base module (matching the existing `auth.py`/`calls.py`/`swml.py` convention of self-contained blueprints): listing resource metadata is one cheap paginated call; fetching each resource's *addresses* is a separate REST call per resource, so metadata is cached in-process for 60s (`_scripts_meta_cache` / `_credentials_meta_cache`) while only the newly-requested page's addresses are fetched fresh, via a small `ThreadPoolExecutor`. `SignalWireClient.list_swml_scripts`/`list_swml_script_addresses` and `list_sip_credentials`/`list_sip_credential_addresses` (`backend/utils/signalwire.py`) all walk their paginated REST endpoint through the shared `_get_all_pages` helper.

Each address carries a `channels` map (`{audio, video, messaging}` → full dial URL, each already suffixed with the right `?channel=...` query string) — dialing the platform in video mode requires using the `video`-channel URL specifically, not just passing `{video: true}` to the SDK's `dial()` call. On the frontend, `DialableResourcesPanel.tsx` renders a two-tab picker (SWML Scripts / SIP Credentials) behind a toggle in `Dialer.tsx`'s header, delegating the actual list/pagination/row UI to the shared, resource-agnostic `ResourceAddressList.tsx` (parameterized by a `fetchPage`/`getRowLabel` pair per tab). Each address row shows labeled Audio and Video buttons; Video is disabled unless a distinct `video` channel URL exists. Selecting either calls `onSelectAddress(path, video)`, which `Dialer.tsx` uses to both fill the dial-pad input and sync the existing `wantsVideo` toggle (so the SDK's local media negotiation matches the channel that was actually selected) — it does not auto-dial.

**Call state is split across three places, deliberately:**
- `SignalWireService` (`frontend/src/services/signalwire.ts`) owns the SDK `Call` objects. It distinguishes `pendingCall` (ringing, not yet answered) from `currentCall` (active). Incoming calls that arrive while `currentCall` is set are auto-rejected.
- `useCallStore` (Zustand) holds UI state — `isInCall`, `isIncoming`, `callStatus`, mute/speaker flags.
- `useSignalWire` is the bridge: it wires SDK callbacks (`onIncomingCall`, `onCallEnded`, `onCallConnected`) into store updates.

**The SignalWire singleton must outlive React unmounts.** `useSignalWire`'s cleanup deliberately does **not** call `signalWireService.disconnect()` — only `App.tsx`'s `beforeunload` listener does. React StrictMode / re-renders would otherwise tear down the registration mid-call. If you need to "reset" the SDK, reload the page; don't try to re-initialize.

**Call reattach is enabled, and that constrains `beforeunload`.** `new SignalWire(...)` passes `reconnectAttachedCalls: true`, so the SDK records each active call in `sessionStorage` and replays those records as `verto.invite` with `reattaching: true` on the next `init()` — this is what carries a live call across a page reload or WebSocket reconnect. Three things hang together and shouldn't be changed in isolation: (1) `App.tsx`'s `beforeunload` listener skips `disconnect()` while `signalWireService.hasActiveCall()` — `client.disconnect()` clears the session's resume state *and* its attach records together, so disconnecting would leave the reloaded page nothing to reattach to; the cost is that closing a tab mid-call no longer hangs up, and the far end waits for the server to time the media out. (2) Reattached calls are pushed straight into `session.calls$`, bypassing both `dial()` and `incomingCalls$`, so `signalwire.ts` subscribes to `calls$` and adopts any untracked non-terminal call into `currentCall` (guarded by `isDialing`, since `dial()` also lands in `calls$` before it resolves). (3) `persistSession` is deliberately left off — see the comment at the `new SignalWire(...)` call for why, and note it would break `switchSubscriber()`. The SDK's own JSDoc on `AttachManager.reattachCalls()` says the server currently rejects reattach with `INVALID_CALL_REFERENCE` pending a FreeSWITCH fix; failures are handled gracefully (records dropped, UI stays on the dialer), so this is wired up ahead of the server side.

**Remote audio has a fallback path.** `remoteStream$` from the SDK isn't always reliable, so `setupRemoteAudioFallback` polls `call.rtcPeerConnection` and attaches a `track` listener directly. Both paths feed `handleRemoteMedia`: a stream with video goes to the remote `<video>` element (which then also plays the audio, so the audio sink is cleared), and audio-only goes to `playRemoteStream`, which renders into a single `<audio id="sw-remote-audio">` element appended to `document.body` (and skips re-assigning tracks it's already playing — both paths deliver the same track in different `MediaStream` wrappers). Don't remove the fallback without verifying audio still works on both inbound and outbound calls.

**Call-ended detection is also redundant.** The SDK's `status$` can fail to emit `disconnected` on certain failures, so `monitorPeerConnection` also treats `iceConnectionState` of `closed`/`failed` and `connectionState` of `closed`/`failed` as call-ended. `endCall()` eagerly calls `handleCallEnded()` before awaiting `call.hangup()` for the same reason — don't reorder.

**Mute is local, not the SDK's `self.mute()`.** The server rejects `call.mute`/`call.unmute` with 403 on 1:1 calls (no `self.mute` capability), and the SDK's fallback stops the mic track and re-acquires it via `getUserMedia` on unmute — measured ~4-5s of silence to the far end. `toggleMute()` instead records the intent in `isMicMuted` (even before the `Call` exists — Mute is live on the "Calling…" screen) and `applyMicMute()` disables both `call.localStream`'s mic track and the outgoing sender track (on answer, `localStream$` emits before the track is attached to the sender). `localStream$` re-applies it when the SDK swaps in a new mic track. `isMicMuted` is reset at the start of `makeCall()`/`answerCall()`/reattach adoption — not in `setupCallSubscriptions()`, which runs after the user may already have tapped Mute.

**Screen share is gated on the `screenshare` capability, per the SDK's screen-sharing guide.** The control shows only when the browser has `getDisplayMedia` *and* `call.self.capabilities.screenshare$` is true. The server grants it on calls into a video room/conference and not on 1:1 calls (browser-to-browser, PSTN, SIP, SWML) — there the share leg is refused ("Must provide a participant invite first", or a 15s `AuxiliaryLegTimeoutError`), because a share attaches to a room *participant*. (Capabilities *are* trustworthy for this; only `hold`/`transfer` aren't in the capability vocabulary at all.) `call.self$` is typed as `CallSelfParticipant`, which doesn't declare `capabilities`, so the code narrows with `instanceof SelfParticipant`; `distinctUntilChanged()` is needed because `self` is replaced on every `call.joined`. `describeScreenShareError()` in `useSignalWire.ts` maps the guide's error table; the sheet disables the row during `starting`/`stopping`; `toggleScreenShare(withAudio)` must run directly from the click (no `await` before `startScreenShare()`, or `getDisplayMedia` loses the user gesture). **`endCall()` stops an active share before `call.hangup()`:** as of 4.0.0-rc.5 `hangup()` only sends `verto.bye` for the main leg, so the share leg's "(Screen)" member otherwise lingers in the room for minutes. Verified on real room and 1:1 calls.

**`call.transfer()` and `call.toggleHold()` resolve even when the server refuses them.** Both are `verto.modify` requests; a refusal comes back nested in a successful envelope (`result.result.error`, observed as -32002 "Permission Denied." on every 1:1 transfer on 4.0.0-rc.5), and the SDK only reports it on `call.errors$` (kind `signaling`, non-fatal). `refusalOf()` in `signalwire.ts` wraps both: `errors$` is a `ReplaySubject(1)` on the asap scheduler, so it lets the replay of the call's previous error pass before arming (otherwise an earlier DTMF/transfer failure is misattributed), runs the request, flushes once more, and returns any refusal for the caller to rethrow. Don't simplify this back to a bare `await call.transfer()`/`toggleHold()`. Hold is purely server-side: no SDP, transceiver-direction, or `mediaDirections` change, and the SDK keeps its hold state in a private `_holdState` that it flips even when the server refuses — so the UI's `isOnHold` is optimistic (reverted on a detected refusal), and there's no client-side signal to verify it.

**The header is shared and its status dot is live.** `StatusBar.tsx` is the top bar for both `Dialer.tsx` and `CallScreen.tsx`: the dot follows `isClientReady` (green, or pulsing amber "Reconnecting…" when `ready$` drops), and the clock ticks on the minute. On desktop/tablet `globals.css` caps `#root` to a phone-width column (not on `short` landscape phones), so the centered title is hidden whenever the bar carries the dialer's header icons except in landscape.

**Window-level key handlers filter their targets.** `Dialer.tsx`'s Enter-to-call ignores Enter from any other input/button (Enter in the Diagnostics field used to dial), and `CallScreen.tsx`'s DTMF listener ignores keys typed into fields (the Transfer destination was being sent as DTMF). Escape closes header panels, the More sheet, and the Transfer modal. Dial-pad keys `preventDefault` on mousedown so clicking them doesn't steal focus from the address input.

**Styling is Tailwind 4 with a JS config.** `globals.css` does `@import 'tailwindcss'` plus `@config '../../tailwind.config.js'`, and defines the project's custom classes (`app-shell`, `glass-*`, `dial-button*`) as `@utility` blocks. `tailwind.config.js` adds a raw `short` screen (`max-height: 500px`) used for side-by-side layouts on phones in landscape; dial-button sizes step down by viewport height in `globals.css`. Tailwind 4 emits media queries in range syntax (`(height<=500px)`), and `hover:` only applies on hover-capable devices.

**Backend "call tracking" is cosmetic.** The frontend fires the `/api/calls/dial` log without awaiting it — awaiting it before `client.dial()` left a window where End was a no-op and the call was placed anyway. `active_calls`/`call_history` in `backend/api/calls.py` are module-level dicts/lists. They don't drive any SDK behavior; they exist for the optional `/api/calls/*` endpoints. The frontend posts to `/api/calls/dial` for logging only — the actual dial happens via `client.dial()` in the browser. Treat the backend call store as ephemeral debugging data, not source of truth.

## Conventions

- The `signalwire-js/` checkout has its own `CLAUDE.md` (e.g. `signalwire-js/packages/main/CLAUDE.md`) — those rules apply when editing files **inside** `signalwire-js/`, not to the dialer code in `frontend/` and `backend/`. In practice you shouldn't be editing the SDK from this repo; consume the npm package instead.
- Phone numbers: frontend and backend both normalize to E.164 (`+1` prefix for 10-digit US numbers). `signalwire.ts:normalizeDestination` (shared by `makeCall` and `transferCall`) and `utils/signalwire.py:format_phone_number` do this — keep them in sync if you change the rules.
- Dial-address detection is also duplicated, deliberately. SIP URIs (`sip:...`) and Fabric addresses (paths starting with `/`) bypass E.164 normalization entirely. Both sides check this independently: `SignalWireClient.is_dial_address` (`backend/utils/signalwire.py`) and the inline `isDialAddress` check in `signalwire.ts:normalizeDestination` (`frontend/src/services/signalwire.ts`). Keep them in sync, same rule as phone-number formatting above.
- Line endings are mixed and there's no `.gitattributes`: many frontend files (e.g. `signalwire.ts`, `Dialer.tsx`, `CallScreen.tsx`, `globals.css`, `package.json`) are CRLF, others are LF. Preserve each file's existing endings — tools that read/write in text mode (e.g. Python's `open().read()`/`write()`) silently convert CRLF to LF and turn a small edit into a whole-file diff.
